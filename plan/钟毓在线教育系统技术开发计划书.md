## 一、项目定位、范围与规模

### 1.1 项目背景（收紧后的问题定义）

核心问题：同一份代码如何让「注册入口 / 账号生命周期 / 授权判定 / 课程可见性」四点由**配置与策略**决定，而不是 `if school_mode`。这四点的**实现载体必须能被单测**：§9.4 的 18 条决策表是唯一判定入口，任何"模式差异"若没进决策表，视为未实现。

### 1.2 核心定位与技术承诺

| 定位 | 技术承诺（可验证） | 验证方式 |
|---|---|---|
| 多环境适配 | 同一份代码 + 同一套迁移，在 SQLite / MySQL / PostgreSQL / **openGauss(5.x/6.x/7.0 三档)** / **KingbaseES V9** 下行为一致 | CI 两档流水线：`ci:main`(3 库) + `ci:domestic`(openGauss 5.x+6.x+7.0、Kingbase V9)；7 条 upsert 用例五库全绿方可发版（§16.2） |
| 双场景模式 | 切换不改表，全站生效 ≤ 30s，存量不丢 | 12 项断言自动比对 + **切换前后进度流水可核对**（`learn_progress_log`） |
| 插件化 | 禁用/卸载任一插件，内核与数据完整可用，残留路由返回 404/403 | 插件契约测试 |
| 进度不丢 | **任意 worker 异常退出、发布回滚、scale-out 场景下，已上报进度丢失 ≤ 1 个上报周期（默认 15s），且绝不发生进度倒退** | `ProgressGateway` 对账用例 HBT-001~006（16.4） |
| 视频防盗链 | ts 进 CDN 长缓存、m3u8 可进 CDN、key 永不经 CDN；票据过期由播放器自动续签，长视频不断播 | §21.4.4 重试注入测试 + 真机 60 分钟播放大考 |

> **另一条不可妥协的承诺**：转码进程崩溃不得影响 Web 可用性，不得产生可被利用的临时文件泄露（§10.3.2.3）。

### 1.3 功能范围裁剪（P0 / P1 / P2）

**P0（必须交付）**：

- 多数据库适配：五库（SQLite / MySQL / PG / openGauss / KingbaseES），**openGauss 必须覆盖 5.x、6.x、7.0 三个大版本档**（7.0 的 `ON CONFLICT` 支持与 5/6 不同，必须在 CI 分档，不能只测 latest）；
- 进度上报：必须走 `ProgressGateway`（§12.5 契约），禁止业务直接写 `learn_progress`；
- 视频播放：必须实现 ts/playlist/key 三层 TTL + 播放器续签（§10.3.4.2）；
- FFmpeg：必须沙箱化（§10.3.2.3），输入前置校验为 P0 门禁。

**P1** 调整：在线充值仍只做状态机 + 通道抽象；学习档案仍列表级；**日志导出与检索优化仍推后**，但 `learn_progress_log` 的追加写入为 P0（它是对账底稿，不是"报表"）。

**P2（后续版本）**：FFmpeg 云转码插件、商用 DRM、离线观看、CDN 多供应商切换。

### 1.4 目标规模与峰值估算

基准：3000 学员 / 200 教师 / 500 课程 / 8000 课时 / 视频 4TB。

```
常规峰值 QPS ≈ 1200 日活 × 40 请求/日 / 86400 × 4.0 ≈ 2.8 QPS
集中登录     ：3000 人 / 300s = 10 QPS 登录；首屏 4 聚合 ≈ 40 QPS
心跳         ：3000 并发 × 1 次/30s = 100 QPS 上报 → §12.5 收敛为 ≤ 5 QPS 落库写
HLS 分片拉流：3000 × 1/4s = 750 req/s ≈ 7.5 Gbps（720p）
```

**关于"100 QPS 落库"**：不能用"每 worker 内存缓冲 + max()"消解——该做法**只对单进程成立**。多 worker（T2 档 2 应用实例）下，同一用户的两次心跳若落在不同 worker，各自的 `max(position)` 分别 flush，**若其中一个 worker 死在 flush 之后、另一个尚未 flush，则较早那次进度会被较晚那次覆盖式丢失**——而 `GREATEST` 只在"两条都到达数据库"时保证不倒退，无法补回没到达的那条。因此：**共享网关 + 单写者落库是满足 §1.2"进度不丢"承诺的唯一实现**。

## 二、总体架构设计

### 2.1 ~ 2.3

选型、分层图、四档拓扑（T0~T3）已定稿。2.2 分层图中的 `Infra Adapters` 层含两个方框：

```
│  ┌── Infra Adapters ────────────────────────────────────────────────┐
│  │ db(适配层+能力探测) storage(Local/S3/OSS) cache(Redis/Null)       │
│  │ queue(DB-backed/Celery) signer(三层TTL) media_runtime(FFmpeg沙箱) │
│  └──────────────────────────┬────────────────────────────────────────┘
```

并在 `learn` 模块内显式画出 **`ProgressGateway`**（进程内 `progress_gw` 单例 → 共享总线的生产者；单写者 `progress-flush` worker 消费），位于 Service 与 Repository 之间，业务代码**不得绕过它写 `learn_progress`**（CI 用 import 路径 + 字符串扫描双检）。

### 2.4 一次典型请求的完整链路（播放）

```
1 浏览器 → GET /api/v1/lessons/{id}/play  (Authorization: Bearer <AT>)
2 Nginx   : TLS 终止、X-ZHY-Request-Id、按 IP+uri 限流、CDN 回源白名单校验
3 InstallGuard : 未安装 → 409 INSTALL_REQUIRED
4 AuthN        : 验签 → typ/jti/tv → 用户快照 → 401 AUTH_*
5 ModeContext  : g.mode 以 config_epoch 为版本，单次请求只读一次
6 AuthZ        : lesson:play + 数据范围
7 AccessPolicy.decide → EventBus.emit("access.check") → Decision
8 MediaService.issue_ticket(lesson, user)        ← 签发票据，不签裸 URL
    ├─ 校验转码就绪？否 → 409 MEDIA_NOT_READY（前端按 retry_after 轮询）
    ├─ 生成 ksession_id = 密码学随机 128bit，存入 media_keysession(ttl, nonce_once)
    ├─ playlist_url = CDN 域名 + master.m3u8 路径 + ?ks={ksession_id}&vp={playlist_ttl}
    │      ↑ kid 与用户无关，故 playlist 可 CDN 长缓存
    ├─ key_url     = /api/v1/media/key/{kid}?ks={ksession_id}&n={nonce}&sig=... （单次 nonce）
    └─ fallback_urls[] = [origin 直出 master.m3u8 的签名版]，CDN 不可达时前端降级
9 返回 { playlist_url, key_url, fallback_urls, expires_in, resume_second,
         profile_allowed, ticket_refresh_url:"/lessons/{id}/ticket", watermark }
10 AuditLog 经事件总线异步落，不阻塞响应
```

**关键点**：第 8 步返回的不是"m3u8 的 120s 签名"，而是**票据（ticket）**。票据与 kid 解耦，使 m3u8 本身成为可缓存的"公共资源"，用户身份只在取 key 的 ksession 里验证；ts 因此可用长 TTL，续签由播放器自动完成。

### 2.5 模块划分与职责边界

| 模块 | 拥有的表 | 对外暴露 | 禁止 |
|---|---|---|---|
| `install` | sys_install_state | `is_installed()` | 依赖业务模块 |
| `config` | sys_config, sys_mode_config, **sys_compat_flags** | `get(key, mode)` / `compat(flavor, cap)` | 默认值写死在代码外 |
| `identity` | account_*, org_*, **account_keysession** | `current_user`, `resolve_scope()` | 判定业务权限细节 |
| `catalog` | edu_* | `subject_tree()`, `course_access_meta()` | 直接读媒体表 |
| `media` | media_*, **media_keysession**, media_usage_daily | `issue_ticket()`, `asset_status()` | 判定谁能看 |
| `assess` | quiz_* | `submit_attempt()`（发 `lesson.finished`） | 直接改学习进度 |
| `learn` | learn_*, **learn_progress_log**, **learn_progress_gate** | `ProgressGateway.record()`（唯一入口）, `profile()` | **禁止直接 INSERT/UPDATE learn_progress** |
| `commerce` | member_*, pay_* | `grant_level()`, `active_sub()` | 侵入 catalog |
| `plugin` | plugin_* | `registry`, `emit()` | 允许插件 import 内部模块 |
| `ops` | sys_log_*, sys_task, **sys_task_lease** | `enqueue()`, `audit()` | 同步阻塞主流程 |

## 三、技术栈定版与选型论证

### 3.1 后端技术栈

各层选型如下：

| 层 | 选型 | 说明 |
|---|---|---|
| 方言能力探测 | `sys_compat_flags` + 安装期 `sys_probe` 临时表冒烟 | 把"方言差异"固化为安装期一次确定的能力位，禁止运行时逐请求探测 |
| 进度共享总线 | T0/T1：`multiprocessing.Queue` + 本地 Unix socket 落盘兜底；T2：**Redis Stream**（`XADD`/`XREADGROUP`，`MAXLEN ~` 兜底）；**接口同一套 `ProgressBus` ABC** | 这是进度网关设计的依据。无 Redis 档**仍**零外部依赖，但 T1 单机上多 worker 通过本地 socket 汇聚到单写者 |
| FFmpeg 沙箱 | `bubblewrap (bwrap)` 首选，次之 `systemd-run --scope` + cgroup v2；容器内需 `seccomp-bpf` 白名单 | 禁止在应用容器内裸跑 ffmpeg |
| 媒体探测 | `ffprobe` 同源版本，输出走 JSON-only（`-print_format json`），**禁用 `-show_entries` 之外的表达式求值**，二次解析用严格 schema 校验 | 防 ffprobe 自身被畸形文件触发 |
| 依赖锁定 | `uv.lock` 精确提交；FFmpeg **不随 pip 安装**，以镜像内二进制 + SBOM 固定版本 | 安全修复时只换镜像层 |

**关于 Python 版本**：3.11 为基线（3.10 最低）。`RETURNING` 能力位在 SA 2.0 下统一走 `DialectCap.returning`（§5.2 D2a），与 PEP 层面的语法无关。

### 3.2 前端技术栈

| 项 | 说明 |
|---|---|
| hls.js | **必须封装一层 `TicketedHls`**（§10.3.4.2 / 23.4）：自定义 `fLoader` 拦截 playlist 与 fragment 请求，403/401 时调 `ticket_refresh_url` 换票并重放**当前 fragment**，最多 2 轮；禁止依赖默认 `xhrSetup` 一把梭 |
| 上传 | 不变；分片 md5 仍 spark-md5 |
| 打包 | 无新增依赖；若 `TicketedHls` 抽成 `packages/media/`，仅内部复用 |

### 3.3 关键取舍

**(4) 为什么进度不交给 Redis 一了百了？**
因为 T0/T1 的"无 Redis 也能跑"是硬承诺（Q8 私有化）。用 Redis Stream 当默认总线，等于把 T0 档废掉。故 `ProgressBus` 抽象：T0/T1 走本地汇聚（单写者进程）+ 进程崩溃时把未 flush 的环形缓冲 fsync 到 `progress_gate.recovery_blob`，重启由 flush worker 重放；T2 走 Redis Stream，失败自动降级本地路径并告警。**两条路径共用同一套对账（watermark），差别只在传输介质。**

**(5) 为什么 m3u8 可以进 CDN？**
前提是"key URI 里不能带用户可辨认的票据"。本方案把票据从 m3u8 里剥离（kid 匿名、ksession 只在取 key 时用、单次 nonce），m3u8 与 ts 一样变成"带一个短期会话参数的公共 playlist"，边缘缓存命中的是同一个字节流，取 key 时才鉴权。**这是 m3u8 可进 CDN 的充要条件，不是放宽安全。**

## 四、后端工程结构与编码规约

### 4.1 目录树

```
zhyonlineedu/
├─ core/
│  ├─ db/
│  │  ├─ types.py            # 不变
│  │  ├─ compat.py           # dialect()/flavor()/cap() + Flavor 枚举覆盖 openGauss/kingbase
│  │  ├─ upsert.py           # 三路编译 + 应用兜底
│  │  ├─ probe.py            # 安装期 sys_probe 冒烟 + sys_compat_flags 固化
│  │  └─ vendor/             # kingbase / opengauss 方言注册（不改 site-packages）
│  ├─ media/
│  │  ├─ signer.py           # 三层 TTL + ksession 票据
│  │  └─ runtime.py          # FFmpeg 沙箱封装
│  └─ progress/
│     ├─ bus.py              # ProgressBus ABC + LocalBus / RedisBus
│     ├─ gateway.py          # ProgressGateway：校验→入队→watermark→对账
│     └─ flush.py            # 单写者：GREATEST upsert + progress_log 追加
├─ modules/learn/
│  ├─ gateway.py             # 唯一对外入口（重导出 core.progress.gateway）
│  └─ repo.py                # 仅 flush worker 调用，禁止被 api/ 层 import
└─ workers/
   ├─ progress-flush.py      # 独立 entrypoint，与 web 进程同镜像不同命令
   └─ transcode.py           # 沙箱化转码入口
```

### 4.2 分层调用规范

1. `api` 层**只允许**调用 `learn.gateway.record()`；`from modules.learn.repo import ...` 在 `api/`、`services/` 下触发 lint 失败。
2. `learn_progress`、`learn_course_progress` 的写入 SQL **必须**形如 `UPDATE ... SET watch_seconds = GREATEST(watch_seconds, :pos)`；出现裸 `= :pos` 的迁移与代码被 `scripts/check_progress_monotonic.py` 拦截。
3. 任何 `INSERT ... ON DUPLICATE KEY UPDATE` / `ON CONFLICT` **必须**经由 `core.db.upsert.upsert()`；裸方言子句直接 fail。
4. FFmpeg 调用**只能**从 `workers/transcode.py` 出发，且参数白名单化（`input_path`、`output_dir`、`profile` 枚举）；禁止把任意字符串拼进命令行（含文件名——文件名先规范化再传入）。

### 4.3 ~ 4.5

统一信封、配置三层模型、装配顺序已定稿。装配顺序中有一条硬约束：**DB 适配层能力探测完成后才允许注册业务 Blueprint**（否则 `/healthz` 返回 `warn:cap_probe_pending`，安装向导据此不开放"开始安装"按钮）。

## 五、多数据库适配层设计（技术核心）

### 5.1 支持的版本矩阵

| 库 | 版本 | `dialect()` | `flavor()` | 关键能力位 |
|---|---|---|---|---|
| SQLite | ≥ 3.35（WAL 支持） | `sqlite` | `sqlite` | returning✅(3.35+)、partial_index✅、conflict_clause✅ |
| MySQL | ≥ 5.7 / 8.0 推荐 | `mysql` | `mysql` | returning❌、on_duplicate✅、native_json✅ |
| PostgreSQL | ≥ 14（9.6 仅兼容，不推荐） | `pg_family` | `postgresql` | returning✅、conflict_clause✅、native_json✅ |
| **openGauss** | **5.x** | `pg_family` | `opengauss_5` | returning❌、**conflict_clause❌**、on_duplicate✅、**7.0 前无 RETURNING** |
| **openGauss** | **6.x** | `pg_family` | `opengauss_6` | 同上（6.x 仍仅 MySQL 风 UPSERT） |
| **openGauss** | **7.0 LTS+** | `pg_family` | `opengauss_7` | returning✅、**conflict_clause✅（7.0 起）** |
| **KingbaseES** | **V9（PG 模式）** | `pg_family` | `kingbase` | returning✅、conflict_clause✅、native_json✅（ora 模式不在承诺范围） |

> **为什么 openGauss 拆三个 flavor**：5.x/6.x 的 UPSERT 语法与 7.0 **不兼容**（7.0 引入 PG 式 `ON CONFLICT`），若只测 latest，CI 会在客户 5.x 上第一周就炸。这是分档的直接理由。Kingbase 以 V9 PG 模式为唯一承诺档；V8R6 及 ora 模式只在"客户介质到位后"作为兼容验证项，不进 `ci:main`。

### 5.2 方言差异清单（编码前必读）

> 下列为方言差异条目，D 编号连续；未单独列出的常规规约（自增主键、JSON、DDL 事务、标识符长度、键长、布尔、大小写、外键、写并发、时区、金额、空串、分页、随机、部分索引、字符集）按 SQLAlchemy 默认语义执行。

| # | 差异点 | SQLite | MySQL | PG / KingbaseV9 | openGauss | 统一做法（强制规约） |
|---|---|---|---|---|---|---|
| D2a | `RETURNING` 作为**取 id 手段** | 3.35+ ✅ | ❌ | ✅ | **5/6 ❌，7.0+ ✅** | **全局禁用** `INSERT ... RETURNING` 取业务 id。单条非冲突插入：`session.add(obj)` + `session.flush()` **仅 PG/SQLite 可靠**；跨方言安全路径 = `flush()` 后读 `obj.id` **仅当** `cap.returning` 为真；upsert 路径**一律按自然键回读**（见 D10a）。能力位 `DialectCap.returning` 由 `sys_compat_flags` 提供，禁止 `try/except` 运行时猜 |
| D10a | UPSERT 编译与**取受影响行 id** | `ON CONFLICT ... DO UPDATE` + `RETURNING id`（3.35+） | `ON DUPLICATE KEY UPDATE` + **`LAST_INSERT_ID()` 不含被更新行 id** | `ON CONFLICT ... DO UPDATE RETURNING id` | 5/6：MySQL 风 `ON DUPLICATE KEY UPDATE`，**无 RETURNING，且不能更新唯一键/主键列**；7.0：`ON CONFLICT ... RETURNING` | 三路编译（`_pg`、`_mysql`、`_og5`）+ 兜底 `select→update/insert + IntegrityError 重试`；**upsert 返回值语义统一为 `UpsertResult(created:bool, pk:PKType \| None, version:int)`，`pk=None` 时必须 `rehydrate_by_natkey()` 回读，调用方不得假设"upsert 一定返回 id"** |
| D19a | 软删除唯一键 | 部分索引 ✅ | 部分索引 ❌（需生成列） | 部分索引 / `NULLS NOT DISTINCT` ✅ | 5/6 接近 PG 行为但**唯一索引含 NULL 语义需实测** | 禁止 `1970-01-01 00:00:00` 单哨兵（同秒双删撞 UK）。统一：`UNIQUE(uq_cols, delete_seq)`，未删 `delete_seq=0`；删除时 `delete_seq = nextval(zhy_delete_seq)`（PG 族）或 `= (UNIX_TIMESTAMP()*1000 + @row_no)` 的 MySQL 等效。**能力位 `cap.soft_delete_composite`**，不支持时 CI 阻断合并 |
| D33 | 序列/自增与批量插入 id 可见性 | AUTOINCREMENT 事后可见 | `LAST_INSERT_ID()` 仅本连接 | `RETURNING` / `curval` | 5/6 同 PG 但 RETURNING 不可用 | 批量插入**不依赖**逐行 id；需要 id 列表时走"先插占位 + 自然键回查"两阶段，`cap.bulk_returning_ids=false` 为全局默认假设 |
| D34 | DDL 与 `ALTER COLUMN TYPE` | 弱 | 可在线（有限） | 可 | 5/6 对类型变更支持面窄 | 迁移一律"加新列→回填→改名→删旧列"四步模板；`render_as_batch=True` 按 flavor 开关，openGauss 强制四步 |
| D35 | 空串 vs NULL（国产库特化） | 区分 | 区分 | 区分 | 受 `password_encryption`/兼容参数影响小 | 代码层**统一 `COALESCE(col,'')=''` 判空**，禁止 `col = ''`；Kingbase **仅承诺 `database_mode=pg` + `ora_input_emptystr_isnull=off`**，安装期 `SHOW` 双检，不符直接 fail-fast |
| D36 | 认证协议 | — | 原生 | scram/md5 | **默认 SHA-256（`password_encryption_type=2`），原生 libpq/psycopg2 直连失败** | 安装期 `db/test` 先走厂商驱动，失败再报"请切 md5 或装定制 psycopg2（需客户安全部门书面同意）"，**禁止静默降级成不安全的明文/trust** |
| D37 | 大小写折叠与双引号 | 折叠 | 不折叠 | 未引号折叠 | 折叠 | 全小写下划线，DDL **永不双引号**，与 26.7 长度核算一致 |

**红线**：任何迁移或模型里出现以下 token，CI 直接失败——`ON DUPLICATE KEY UPDATE`（裸写）、`ON CONFLICT`（裸写）、`RETURNING`（裸写，允许在 `upsert.py` 内部按能力位生成）、`ROWNUM`、`NVL`、`DECODE`、`(+)`，以及 Kingbase/OG 厂商扩展函数。

```python
# 软删除：统一复合唯一，消除"同秒双删撞键"（D19a）

class SoftDeleteMixin:
    deleted_at:  Mapped[datetime | None] = mapped_column(UTCDatetime, nullable=True, default=None)

    # 唯一键：UniqueConstraint(*uq_cols, "delete_seq")  ← 由 Base 元类按 __table_args__ 注入
```

**`upsert()` 契约（写进 docstring 即测试依据）**：

1. 不抛 `IntegrityError` 给调用方；冲突重试最多 2 次，仍冲突则返 `UpsertResult(conflict=True, pk=None)`；
2. 绝不更新自然键列与主键列（openGauss 5/6 硬限制，违反即 SQL 报错）；
3. `version` 列存在时自动 `+1`，用于进度对账；
4. 批量模式下**单条失败不中断整批**，失败行进 `UpsertBatchReport` 供告警；
5. 生成的 SQL 必须可通过 `scripts/explain_upsert.py <flavor>` 文本比对，禁止黑盒拼接。

### 5.6 迁移策略

- 安装：`create_all` 仅用于**全新空库**；升级一律 Alembic。
- Alembic `env.py` 注入 `context.configure(rendered_item_type_requires_batch=flavor_needs_batch(flavor()))`；openGauss / Kingbase 自动走四步模板，禁止自动生成"直接 `ALTER COLUMN TYPE`"的迁移脚本。
- 每条迁移脚本头部声明 `x-zhy-cap` 元数据：`# x-zhy-cap: returning:optional, alter_type_online:false`。CI 在 `ci:domestic` 上用目标 flavor 实跑 `upgrade head` + `downgrade base`，`ci:main` 只跑 SQLite/MySQL/PG。
- 插件迁移链不变，但插件表**必须**含 `delete_seq`（D19a），`core/db/plugin_migration.py` 在加载插件 DDL 时注入并断言。
- **回滚前提**：迁移前 `sys_install_state` 已记录 `last_good_rev`；失败由 `manage.py db-migrate --rollback-to-last-good` 触发（先逻辑校验再执行，MySQL DDL 不可事务，需从备份恢复，文档明确提示）。

### 5.7 数据库间数据搬迁（换库）设计

换库（SQLite → PG / MySQL → openGauss）流程：① `db probe` 跑能力位；② 按 flavor 生成**目标 DDL**（同一 metadata，禁手动改）；③ 逻辑导出为 `COPY`/`LOAD DATA` 分批流，禁用外键检查仅在导入窗口内；④ 导出前对每张软删表校验 `delete_seq` 唯一性（防源库历史脏数据在目标库撞 UK）；⑤ 校验行数 + `CHECKSUM TABLE` 级聚合哈希；⑥ 切换 `sys_install_state.schema_rev` 并停写旧库。

```python
# core/progress/gateway.py  —— 业务只能调这个
def record(self, cmd: ProgressCmd) -> RecordReceipt:
    assert cmd.position >= 0 and cmd.played_seconds >= 0
    cmd = cmd.with_gw_seq(self._next_gw_seq())      # 全局单调，崩溃安全
    self.bus.publish(cmd)                          # 本地 socket / Redis Stream
    self._maybe_ack_to_log(cmd)                    # T0 直通：直接落 log，不走网络
    return RecordReceipt(accepted=True, gw_seq=cmd.gw_seq)

# core/progress/flush.py  —— 唯一 writer
def flush_once(self):
    with self._acquire_lease(shard="default", ttl=30):   # 抢不到就退出，别抢
        batch = self.bus.drain(max=200, timeout_ms=50)
        for cmd in batch:
            stmt = (
                insert(ProgressLog).values(**as_log(cmd))
                .on_conflict_do_nothing(...) if pg/sqlite else
                insert(...).prefix_with("IGNORE")        # MySQL：gw_seq 唯一兜底
            )
            session.execute(stmt)
        # 聚合：每个 (user,lesson) 取 max(position)、sum(1x 折算 played)
        for (u, l), agg in self._fold(batch):
            session.execute(
                update(Progress)
                .where(Progress.user_id == u, Progress.lesson_id == l,
                       Progress.version == agg.expected_version)
                .values(watch_seconds=func.GREATEST(Progress.watch_seconds, agg.max_pos),
                        last_position=func.GREATEST(Progress.last_position, agg.max_pos),
                        version=Progress.version + 1, ...)
            )
            # version 冲突 → 整批 continue 后由下次重读，绝不以旧值覆盖
        self._advance(last_gw_seq=batch[-1].gw_seq)
```

**为什么不丢**：gw_seq 在入队前就分配并先写 `progress_log`（追加、无冲突），flush 失败可无限重放；`learn_progress` 只是"视图态"，丢了能从 log 重建。`learn_progress_gate.last_gw_seq` 是幂等水位，发布回滚 / 多实例只会有一次生效。

**容量**：100 QPS 上报 × 30s 缓冲 = 3000 条/log 周期；`progress_log` 按月分区（或定期归档到 `progress_log_archive`），保留 90 天可配。3000 人 × 40 分钟/日 × 2 次上报/分钟 ≈ **24 万条/日 ≈ 7.2M/月 ≈ 1.4GB（含索引）**，90 天 ≈ 4.3GB，远低于 4TB 视频占比，可接受。

## 七、认证与权限体系

### 7.1 令牌方案

结论（RS256 / AT 30min / RT 14d / HttpOnly Cookie / `tv` / `sid`）为定稿。其中"改密窗口"的口径明确如下：

> **`token_version` 不是"秒级下线"机制，是"窗口式下线"机制。** AT 是无状态的，tv 递增后旧 AT 在 `exp` 之前仍可通过验签；本系统定义为：**旧 AT 最长可用时间 = `ZHY_AUTH_AT_TTL`（默认 30min，可压到 30s 做强控）**，无 Redis 档下接受该窗口，把它写进威胁模型与验收用例（`AUTH-TV-WINDOW`）。若客户要求"改密即 1 秒内全端失效"，那是 **T2 档专属能力**（Redis `token:jti:{jti}` 短黑名单 + 强制踢 sid），不作为默认承诺，避免为它引入 Redis 硬依赖。

ksession **不进 JWT**（票据走 `media_keysession` 表）：若把 ksession 塞进 JWT，m3u8 就无法在 CDN 缓存。

### 7.2 主动失效与"改密即全端下线"

失效机制由 tv 递增 + sid 吊销 + RT 重放即全端下线构成。此外：`account_session` 增 `revoked_by` 与 `revoke_reason`（`password_change`/`admin_kick`/`suspect_replay`），供审计；RT 重放触发的不只是 tv+1，还要写 `sys_log_security(event=AUTH_REFRESH_REPLAY)` 并告警（可能是令牌窃取）。

### 7.3 RBAC 模型

RBAC 为三层结构（用户-角色-权限码），内置权限码如下（附录 C 同步）：

| 权限码 | 用途 | 风险级 |
|---|---|---|
| `progress:direct` | 绕过 ProgressGateway 直写（**仅内部运维命令可用**） | 高危，默认无角色持有 |
| `media:key:any` | 跨用户取 key（风控/客服核查） | 高危，审计强记 |
| `system:cap_probe` | 重跑能力探测、查看 `sys_compat_flags` | 中 |

### 7.4 认证与权限的失败路径

票据与播放相关的错误码映射：

| 场景 | 错误码 | 前端行为 |
|---|---|---|
| ksession 过期 / nonce 已用 | `MEDIA_TICKET_EXPIRED`(40201) | 静默调 `ticket_refresh_url` 换票重试 1 次，失败才弹"请重试" |
| ksession 与 lesson 不匹配（串课） | `MEDIA_TICKET_MISMATCH`(40203) | 停止播放，回课程页 |
| 取 key 被风控吊销 | `MEDIA_ACCESS_REVOKED`(40204) | 提示"会话已失效，请重新进入课时" |
| 播放器连续 3 次 fragment 403 | `MEDIA_PLAYBACK_UNRECOVERABLE`(40205) | 切 origin 回落失败 → 展示客服入口 |

### 7.5 前端权限控制

路由守卫对 `MEDIA_TICKET_EXPIRED` **不跳登录**，只触发换票；避免"播着播着被踢到登录页"的误伤。

### 8.5 安装期安全

安装向导 **`POST /install/db/test`** 现在是能力探测入口，返回：

```json
{ "ok": true, "flavor": "opengauss_6", "dialect": "pg_family",
  "caps": { "returning": false, "upsert_conflict_clause": false,
            "upsert_on_duplicate": true, "soft_delete_composite": true,
            "native_json": true, "alter_type_online": false },
  "warnings": ["openGauss 6.x: UPSERT 无 RETURNING，已启用应用层回读路径"],
```

`blockers` 非空则前端"下一步"置灰。当前定义的 blocker：
1. `database_mode != pg`（Kingbase）或无法 `SHOW` 确认；
2. `ora_input_emptystr_isnull=on`（Kingbase，空串转 NULL 造成语义污染）；
3. 驱动加载失败（缺 `libkci.so` / openGauss psycopg2）；
4. 建库字符集非 UTF8；
5. `upsert` 冒烟失败（sys_probe 临时表 INSERT 冲突后回读 id 一致）——安装放行的必过门禁。

`/install/finish` 把 `caps` 快照写入 `sys_compat_flags`（`probed_at`、`probe_blob` 可回放），**之后所有 `core.db.cap()` 只读这张表**，不再碰数据库做特性探测。

## 九、双场景模式的实现机制

### 9.1 ~ 9.2

## 十、核心功能模块细化设计

### 10.1 学科树 / 10.2 课程与课时

两处加固：
- 拖拽排序的 `sort_order` 步进 1024，移动节点用 `UPDATE ... WHERE id IN (...)` 单条事务，加 `version` 乐观锁，并发拖拽后到的请求返 `CONFLICT_RETRY`（409），前端提示"列表已更新，请重试"，避免覆盖他人排序。
- 课程 `publish` 校验调用 `MediaService.asset_readiness(course)`：任一课时 asset 无 `encoded` 完成态即拒发，返 `COURSE_ASSET_NOT_READY` 并附未就绪课时清单——避免"上架了但播放全 409"。

### 10.3 视频链路（风险最高的一段）

#### 10.3.1 上传

流程（秒传 / 断点 / 分片 / 合并 / 入队）之外，另有两条安全加固：

1. `complete` 阶段复核整体 sha256 后，**先 ffprobe 输入魔数**：`ffprobe -v error -show_entries format=format_name,duration,size -of json input`；`format_name` 不在白名单（`mp4,mov,mkv,flv,webm,mp3,aac` 按项目配置）立即 `UPLOAD_MALICIOUS(50103)` 并删除临时文件，不进转码队列。**这是转码安全的第一道门，必须在 Web 进程里做，不能等转码 worker。**
2. 分片临时文件设 `O_CREAT|O_EXCL` + 目录 `mode 0700`、属主非 root；合并后 tmp 文件 10 分钟未消费由 `tmp-reaper` 清理，防磁盘被分片塞满。

#### 10.3.2 转码（含 §10.3.2.3 沙箱）

##### 10.3.2.1 码率阶梯

码率阶梯为 360p/720p/1080p。`profile` 由**服务端按 AccessPolicy 裁剪**：`hls_profile_set` 存 `{"360","720"}` 或加 `{"1080"}`；`issue_ticket` 只签发被授权档位的 variant URL，未授权档位**不出现在 master.m3u8 里**（第 9.4 #17 的落地），禁止前端"切清晰度绕过会员"。

##### 10.3.2.2 命令骨架（不变处略）

```bash
# 输入经白名单化：-- 用双横线隔离选项，路径用 ./ 前缀，禁 $var 直接拼接
ffmpeg -y -f lavfi -i "movie=filename=./${SAFE_IN}" ...   # 实际用 -i "$ABS_PATH"，ABS_PATH 经 realpath 校验在允许目录内
  -filter_complex "[0:v]split=3[v1][v2][v3];[v1]scale=1280:720:force_original_aspect_ratio=decrease[v1o];..." \
  -map "[v1o]" -c:v:0 libx264 -preset veryfast -crf 23 -b:v:0 3000k -profile:v:0 high -level 4.1 \
      -g 48 -sc_threshold 0 -keyint_min 48 -r 25 \
  -map 0:a? -c:a aac -b:a:0 96k -ar 44100 \
  -f hls -hls_time 4 -hls_list_size 0 -hls_playlist_type vod \
  -hls_segment_filename "${OUT}/seg_%v_%03d.ts" \
  -hls_key_info_file "${KEYINFO}" \
  "${OUT}/master_%v.m3u8"
```
（`-hls_time 4`、`-keyint_min` 与 gop 对齐，保证切片边界可寻址；音频流用 `0:a?` 避免无声文件崩溃。）

##### 10.3.2.3 转码沙箱（P0 门禁）

**原则：输入是攻击者提供的字节流，FFmpeg 是解析器，解析器有历史 CVE。**

| 层 | 措施 | 实现 |
|---|---|---|
| ① 输入检疫 | 魔数 + 时长/尺寸上限 | Web 进程 ffprobe 白名单；`max_duration_sec=14400`、`max_dimension=4096`，超则拒 |
| ② 权限降权 | 非 root、无家目录、无 TTY | `bwrap --unshare-all --ro-bind /usr,/lib,... --bind "$OUT" --chdir /tmp/transcode --uid 65534 --gid 65534`；或 systemd `--no-new-privileges` |
| ③ 网络 | **完全无网** | `bwrap` 不挂 netns / seccomp 禁 `socket(AF_INET*)`；防恶意文件触发回调外联或 SSRF 式探针 |
| ④ 资源 | CPU / 内存 / 进程数 / 文件数 | cgroup v2：`cpu.max=200000 100000`（2 核）、`memory.max=2G`、`pids.max=16`；`ulimit -f`（输出字节上限）双保险 |
| ⑤ 系统调用 | 白名单 | seccomp-bpf 允许 `read/write/close/openat/mmap/munmap/brk/futex/...`，**禁** `mount`,`ptrace`,`process_vm_readv`,`unshare`,`execve` 外的非常规调用；容器镜像提供 `/etc/seccomp/zhy-ffmpeg.json` |
| ⑥ 输出校验 | 产物不可信 | 转码后 **再跑 ffprobe**，校验：`format_name==hls`、所有 ts 的 `codec_name` 在白名单、无外部引用、`duration` 与源误差 <2%、ts 字节数 >0；不符则整个 asset 标 `failed`，**不**更新 `playlist_version` |
| ⑦ 凭证隔离 | keyinfo 文件 | AES 密钥只以 `0400` 临时文件注入沙箱，退出即 `shred`；**禁止**把主密钥、数据库 URL、JWT 公钥写进环境变量可见区 |
| ⑧ 失败处置 | 不回吐 stderr 给前端 | 前端只看到 `转码失败（错误码 ENC-xxxx）`；stderr 尾部 2KB 仅落 `media_transcode_job.err` + 管理员可见，避免路径/文件名泄露 |

**交付物**：`deploy/ffmpeg/seccomp.json`、`deploy/ffmpeg/bwrap-launcher.sh`、`deploy/ffmpeg/policy.yaml`（声明资源配额，可按 T1/T2 档覆盖）。离线镜像必须把 `bubblewrap` 与 `ffmpeg` 静态构建产物一起打进 `deps` 层（24.2），否则客户内网无法跑转码。

**[实测结论（M2.4）2026-10-30]** ⑥ 的 codec 校验有一个必须显式处理的细节：HLS 分片是 AES-128-CBC 密文，`ffprobe` 直接探测恒为 `unknown`（会被白名单判成 `codec_not_allowed`）。实现先按 `#EXT-X-KEY` 的 `IV`（`core/media/hls.py::Variant.iv`）与任务注入的 key 解密首片（`core/media/keys.py::decrypt_aes128_cbc`），再交给探测；明文副本只写入 `codec-probe/` 临时目录并在 `finally` 删除，**绝不进入发布产物**。回归用例见 `tests/test_transcode.py`（IV 解析 / 解密往返 / 解密探测 / 端到端加密产物转码）。

**事故响应（CVE 处理原则，写进 18/19）**：新 FFmpeg CVE 公布 → `doctor` 加一条版本检测 → 比对 SBOM → 若命中解析器链路：**停止新任务入队**（`media.transcode.paused=true`），已上传文件保留；升级镜像层后跑回归用例 T-MEDIA-FF-001~004（畸形 box / 超长 artifact / 递归索引 / 负数 duration）再恢复。禁止"边跑边等补丁"。

#### 10.3.3 加密与防盗链（票据 + 三层 TTL）

| 层 | 做法 |
|---|---|
| L1 目录隔离 | 媒体按域分离：**m3u8 与 ts 同域 CDN，key 只走应用** |
| L2 签名 | **三层 TTL + ksession 票据**；IP 仅作软信号 |
| L3 AES-128 | `#EXT-X-KEY` 指向 `/key/{kid}`；kid **与用户解耦**，key URI 带 `ksession` + 单次 `nonce`，原生 HLS 可拿 key（23.4） |
| L4 水印 | DOM 叠加，移动端同样 |
| L5 DRM | 暂不做（L1~L4 覆盖） |

**核心模型：票（ticket）而不是签名 URL**

```
┌──────────── 匿名、可缓存层（CDN 可长缓存）────────────┐
│  master.m3u8 / variant_720.m3u8 / seg_720_001.ts      │
│  → 这些字节对所有持有效 ksession 的用户完全相同        │
│  → playlist 内 #EXT-X-KEY:URI=".../key/{kid}?ks=..&n=.." │
└──────────────────────────────────────────────────────┘
           ▲ 鉴权只发生在这里
┌──────────── 用户绑定层（永不进 CDN）────────────┐
│  GET /media/key/{kid}?ks={ksession_id}&n={nonce}&sig │
│  校验：ksession 归属 + 未过期 + lesson 匹配 + nonce 首次 │
│        + access_decision_hash 与当前策略一致          │
│  成功：返回 16 字节 AES key（Content-Type application/octet-stream）│
│  失败：403 + `MEDIA_TICKET_*` 码，播放器换票重试      │
└──────────────────────────────────────────└
```

**为什么这是对的**：kid 是 asset 属性（一个视频一个 kid），m3u8 因而变成"静态资源"，CDN 命中率极高；用户身份只出现在取 key 的这一次调用里，且 nonce 单次有效，边缘节点即便回放这个 key 请求也拿不到明文。**这同时消除了 m3u8 带用户票据进 CDN 的越权风险，m3u8 可以放心上 CDN。**

**三层 TTL**——长视频连续播放的前提：

| 层级 | 配置 | 典型值 | 说明 |
|---|---|---|---|
| `media.ts_ttl` | 长 | **24h ~ 7d** | ts 是 AES 密文 + ksession 已验过才拿得到 key，泄露价值极低；长 TTL 是 CDN 命中率与回源成本的来源。**ts URL 不设短 TTL，否则长视频每 2 分钟一片 403** |
| `media.playlist_ttl` | 中 | **5~15min** | master.m3u8 含 key URI（带 nonce 会失效），不能太长；5 分钟足够一次长播，过期由播放器换票后重新拿 playlist |
| `media.key_ttl` | 短 | **120s**，nonce **单次** | key 是明文密钥的最后一道门，最严 |

`GET /lessons/{id}/play` 返回的是 `ticket`，不是裸 URL：

```json
{ "playlist_url": "https://cdn.example.com/c/asset/128/master.m3u8?ks=ks_01...&vp=900",
  "key_url":      "https://api.example.com/api/v1/media/key/aes_128_abc?ks=ks_01...&n=nonce&sig=...",
  "ticket_refresh_url": "/api/v1/lessons/128/ticket",   // 换票接口
  "ticket_ttl_sec": 900,  "key_ttl_sec": 120,
  "fallback_urls": ["https://origin.example.com/c/asset/128/master.m3u8?ks=..."],
  "profile_allowed": ["360","720"], "resume_second": 142,
  "watermark": {"text":"学号***23｜2026-10-28","enabled":true} }
```

`POST /lessons/{id}/ticket`（见 §15.2 的 82 接口清单）：**幂等换票**。前置 `lesson:play` 重判（策略可能已变，如会员刚到期），签发新 ksession、旧 ksession 保留 30s 防在途 key 请求失败，返新 `playlist_url/key_url/ticket_ttl_sec`。续签因此不需要客户端持有长效凭证。

**IP 绑定处置**：`ksession.ip_family` 只记 `/24`(v4) 或 `/56`(v6)，校验**不匹配只记日志、不拒**（4G 切网 / 微信复用连接会漂）。若客户合规明确要求"严格绑定"，需显式开启 `media.ksession.strict_ip=true` 并接受"移动端误杀率上升"作为已知代价，写进验收附录。

#### 10.3.4 播放与进度上报

##### 10.3.4.1 播放器（前端）

`packages/media/TicketedHls.ts` 封装 hls.js，**禁止业务直接 `new Hls()`**：

```ts
export class TicketedHls {
  private hls = new Hls({ /* 禁用默认 xhrSetup 的裸 Authorization 透传 */ })
  constructor(private ctx: PlayCtx) {
    this.hls.config.xhrSetup = (xhr, url) => this.intercept(xhr, url)
    this.hls.on(Hls.Events.ERROR, (_e, data) => this.onHlsError(data))
  }
  // 拦截三类请求：playlist / fragment / key
  private intercept(xhr: XMLHttpRequest, url: string) {
    if (isKey(url)) { xhr.open('GET', url, true); xhr.setRequestHeader('Authorization', `Bearer ${this.ctx.at}`); return } // key 需 AT
    if (isPlaylist(url)) { xhr.open('GET', url, true); return } // CDN 直出，无头
    // fragment：hls.js 默认不带自定义头 → 正好，CDN 按签名/鉴权 key 放行
  }
  private async onHlsError(data: HlsErrorData) {
    const fatal = data.type === Hls.ErrorTypes.NETWORK_ERROR &&
                 (data.response?.code === 401 || data.response?.code === 403)
    if (!fatal || this.retries >= 2) { this.ctx.onUnrecoverable(40205); return }
    // ★ 核心：fragment/playlist 403 ≠ 直接报错，先换票再重放当前片段
    const t = await fetchTicket(this.ctx.lessonId)   // POST /ticket，幂等
    this.retries++
    this.hls.swapAudioCodec?.()                       // noop 占位
    this.hls.loadSource(t.playlist_url)              // 换 playlist（新 ksession）
    this.hls.startLoad(data.frag?.start ?? this.ctx.resumeSec)
  }
}
```

iOS **关键点**：`canPlayType('application/vnd.apple.mpegurl')` 为真时用原生 `<video src>`，**key 请求无法加 Authorization 头**——因此 key_url 必须支持 query-string 票据（`ks`+`n`+`sig`），与原生、hls.js 两条路径共用同一 URL。`TicketedHls` 在原生模式下只负责"403 时 fetch `/ticket` 再 `video.src = newPlaylist`"，逻辑同构。这就是 23.4 那条"PC 能放手机不能放"头号成因的终局解法。

##### 10.3.4.2 进度上报

```ts
// 每 30s 且位置变化时；用 navigator.sendBeacon 兜底
const cmd = { lessonId, position, playedSeconds, speed, gwSeq: await getGwSeq() }
navigator.sendBeacon('/api/v1/lessons/{id}/progress', JSON.stringify(cmd))
// 后台/锁屏：pagehide + visibilitychange，fetch(keepalive:true) 兜底，再兜底"下次进入靠服务端 max 补齐"
```

服务端 `POST /lessons/{id}/progress` **只做三件事**：

1. 验权（lesson:play）+ 防篡改：`gw_seq` 单调校验（可选，重放直接 202 忽略）；
2. `ProgressGateway.record(cmd)` → 入总线，立即返 `202 PROGRESS_ACCEPTED{gw_seq}`（**不**等落库：HTTP 层不阻塞、不承诺已持久化）；
3. `resume_second` 的"已确认位置"从 `learn_progress.last_position` 读，**不是**本次上报值——保证客户端刷新后不回跳。

**禁止"每 worker 内存 dict + max 落库"**：该做法在多 worker + 进程异常下不成立（理由见 §1.4）。该契约的验收三条：
- **不倒退**：任意并发/乱序/重放，`watch_seconds` 单调不减（`GREATEST` + `version` 乐观锁）；
- **不丢**：进程 `kill -9` 后，`progress_log` 中 `gw_seq` 连续，`last_gw_seq` 之后的条目由恢复 worker 重放；
- **不双计**：`played_seconds` 按 1x 折算后用"滑动窗口去重窗口"（同 (user,lesson,position_bucket=position/30s) 只计一次），避免 30s 一次上报被当成真实观看时长翻倍。

**完成判定**：`percent >= completion_threshold(90)` 且**最近一次位置连续 ≥ duration*0.9**（防"拖到结尾即完成"），发 `lesson.finished` 事件；插件（证书/积分）订阅该事件，不在进度写入路径里同步执行。

##### 10.3.4.3 倍速与合规口径

`speed` 上报 + `speed_time`（按 1x 折算）。`progress_log.speed_time` 派生规则：`speed_time = played_seconds / speed` 取整；报表明确区分"屏幕时长"与"有效时长"，并在导出文件页眉印口径版本（防学校统计口径扯皮，属审计要求）。

### 11.1 ~ 11.8、11.10

插件体系由三级扩展、manifest、生命周期、事件总线、独立迁移链、前端接入与审核清单构成。落地口径（`core/plugin/`、`modules/plugin/`、`web/src/stores/plugin.ts`）：

## 十二、异步任务与定时调度

### 12.1 需要异步的操作清单

异步任务清单：`progress-flush`（单写者）、`progress-recovery`（崩溃补偿）、`cdn-prefetch`、`cdn-usage-poll`、`transcode`（沙箱化）、`ffmpeg-cve-check`（每日 SBOM 比对）。

### 12.2 为什么默认不用 Celery

`progress-flush` 的语义是"至少一次 + 有序 + 单写者"，Celery 的 at-least-once + 预取会让两个 worker 同时 flush 同一 gw_seq 区间；故 T2 档也**先用 Redis Stream + 单消费者组**，只有"任务类型需要 fan-out / 延迟重试"时才上 Celery，且仍走 `TaskQueue` 抽象。

### 12.3 `sys_task` 表与 worker

| 字段 | 说明 |
|---|---|
| `dedup_key` UK | 不变 |
| **`lease_owner` / `lease_until`** | 单写者租约，flush worker 抢占用；替代"靠 DB 唯一索引撞锁"的脆弱做法 |
| **`progress_gw_seq_from/to`** | flush 类任务标记水位，恢复时可读 |
| `max_attempt / attempt` | 不变；flush 任务 `max_attempt=0`（永久重试，靠人工停） |

worker 主循环：SIGTERM → 完成当前 batch + `release_lease()` 再退；**禁止** `-9` 式强杀（systemd `TimeoutStopSec=60`）。`progress-flush` 与 `transcode` **强制分进程、分 cgroup、分用户**，转码炸不影响进度写入。

### 12.4 定时任务

防重入用 `dedup_key=日期+任务名`。任务清单：

| 任务 | 频率 | 说明 |
|---|---|---|
| 进度 flush | 常驻（≈5s） | `progress-flush` 常驻进程，不由 scheduler 触发（秒级节奏 scheduler 不稳） |
| 进度对账 `progress-reconcile` | 5min |`SELECT last_gw_seq FROM gate` 对比 `MAX(progress_log.gw_seq)`，缺口 >0 则告警 + 触发 recovery；检测"worker 假死未丢数据"与"丢数据"两态 |
| 进度日志归档 | 每日 03:00 |>90 天的 `progress_log` 挪 `progress_log_archive`，防无限膨胀 |
| 会员/账号过期 | 每日 02:00 | 不变 |
| 订单查单补偿 | 5min | 不变 |
| 转码僵尸巡检 | 5min | 不变 |
| **FFmpeg SBOM 比对** | 每日 |离线环境比对内置 hash 清单，有 CVE 命中 → `media.transcode.paused=true` + 告警 |
| CDN 用量拉取 | 每小时 | 不变 |

### 12.5 进度心跳网关

> **必须避免的做法**：*"无 Redis 且多 worker 时，各 worker 私有缓冲按 max() 落库仍正确，仅写入翻倍。"*
> **为何不成立**：`max(position)` 只在两条记录**都到达数据库**时保证不倒退。若 worker-W1 缓冲了 position=420 但尚未 flush 即被 kill，worker-W2 随后 flush position=300，则数据库定格在 300——**用户确已观看的 2 分钟静默消失**，且这种丢失在监控上不可见（没有报错，只是进度"没涨"）。SQLite WAL 只解读写互斥，救不了应用层缓冲丢失。

**网关契约（唯一正确形态）**

```
                    ┌────────────────────────────────────────────┐
  N 个 web worker   │  ProgressGateway.record()                 │
  (每请求 <1ms)     │    cmd.with_gw_seq(单调) → bus.publish()  │
                    └───────────────────┬────────────────────────┘
                                        │ 本地 Unix socket / Redis Stream
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │  progress-flush （单写者，单实例/shard）     │
                    │  ① 抢 lease(shard) → 失败即退，绝不并行     │
                    │  ② drain 200 条 → 先 append progress_log    │
                    │  ③ fold：per (user,lesson) GREATEST(pos)    │
                    │  ④ UPDATE progress SET ...=GREATEST(...)     │
                    │       WHERE version=:expect  （失败→下轮重读）│
                    │  ⑤ advance(last_gw_seq) + release_lease()   │
                    └────────────────────────────────────────────┘
                                        │ 崩溃/重启
                                        ▼
                    ┌────────────────────────────────────────────┐
                    │  progress-recovery（对账）                  │
                    │  gate.last_gw_seq < MAX(log.gw_seq)         │
                    │    → 重放缺口区间，幂等（log 已存在不重插） │
                    └────────────────────────────────────────────┘
```

**T0/T1（无 Redis）的实现**：`bus.LocalBus` = 每个 web worker 把 cmd 序列化到 **`$RUNTIME_DIR/progress/<worker_pid>.ring`**（mmap 环形缓冲，`O_DIRECT` 可选），`progress-flush` 启动时扫全部 ring 文件、按 `gw_seq` 归并。`flush` 进程本身被 systemd 保活；web worker 在 `atexit` + `SIGTERM` 里对**自己那份 ring 做 `fsync`**，保证"进程死、数据还在磁盘"。这是零外部依赖下"不丢"的唯一可行结构。

**T2（有 Redis）**：`bus.RedisBus` 用 `XADD zhy:progress {json} ID *` + `XGROUP CREATE` 单消费者组，`progress-flush` `XREADGROUP` 阻塞；`progress_log` 仍落 DB（bus 只做传输，DB 才是真相源）。Redis 不可用时 bus 自动降级 LocalBus 并 `WARN_REDIS_DEGRADED`，进度**继续可用**，只是多实例间短暂重复入队——`progress_log.gw_seq` UK 兜底去重。

**一致性强度声明（写进 SLA）**：

| 场景 | 进度丢失上限 | 说明 |
|---|---|---|
| 单 web 进程正常 | 0 | 同步 append log |
| web worker kill -9 | ≤ 1 个上报周期（30s）内、且仅该 worker 未 fsync 的部分 | ring 已 fsync 的部分由 recovery 补 |
| `progress-flush` kill -9 | 0（对使用者可见） | log 已落，下次启动重放；可能出现"已上报但未反映到进度条"≤15s，前端展示 `saving` 态 |
| Redis 宕 + 多 web 实例 | 重复入队 ≠ 丢失 | log 的 gw_seq UK 去重，progress 仍 GREATEST |
| 发布回滚 / scale-in | 0 | gate 水位 + log 重放 |

**验收用例（HBT-001~006，对应 §16.4）**：① 双 worker 并发同用户不同 position，最终 = max；② worker-A 入队后 kill -9，重启后值补齐；③ flush 进程双起，只有一个拿到 lease，第二个空转；④ version 冲突注入（两个 flush 同时写），无覆盖、无报错、最终一致；⑤ 乱序到达（pos=600 先于 pos=300），结果=600；⑥ 100 QPS 压 5 分钟，`progress_log` gw_seq 无缺口、`learn_progress.watch_seconds` 与"客户端累计最大值"误差为 0。

### 13.3 安全设计

安全条目（编号续接前文）：

- **S-UPLOAD 输入检疫**：10.3.1 魔数 + 时长/尺寸上限，恶意文件不进队列。
- **S-TRANSCODE 沙箱**：10.3.2.3 八层，含 seccomp、无网、非 root、输出二次 ffprobe。FFmpeg 版本纳入 SBOM 与 `doctor`，CVE 响应流程入 18/19。
- **S-TICKET 票据模型**：ksession 单次 nonce、不绑精确 IP、kid 匿名、m3u8 可缓存、key 永不进 CDN。禁止把 ksession / key 材料写进日志、埋点、Referer。
- **S-PROGRESS 防篡改**：gw_seq 单调 + `progress_log` 追加-only + `source=preview` 隔离，防止"刷接口刷进度"（前端倍速折算已做，此处再加接口级滑动窗口配额：`progress:upsert:/lesson/{id} = 2/min`，超则 429，不影响观看）。
- **S-COMMAND 注入**：FFmpeg / 数据库 / 迁移的所有参数白名单化；文件名 `realpath` 后校验在允许目录内，禁 `$VAR` 拼接。
- **S-SECRET 零落盘**：转码 keyinfo 0400 + 退出 shred；JWT 私钥只在启动期进内存，不写磁盘、不进 `/install/finish` 回显。
- **依赖供应链**：`uv.lock` + `pip-audit` + `osv-scanner` 进 CI；FFmpeg 单独 SBOM，与 PyPI 依赖分开扫描。

### 13.4 可靠性、单点与兜底

可靠性按三层模型设计：

- **进度**的单点是 `progress-flush` → 用 **shard 租约 + 进程双活抢不到即退** 消除脑裂，数据真相在 `progress_log`，所以"flush 挂掉"只表现为进度延迟，不表现为丢数据（这是把单点从"数据"降级成"延迟"的关键重构）。
- **CDN 兜底**：`fallback_urls` 指 origin；`doctor` 测 CDN 连通性 + 命中率抽样，连续 3 次失败自动把 `media.sign_mode` 切 `origin`（可配置），恢复后回切需人工确认，避免抖动来回跳。
- **改密窗口**：tv 递增后旧 AT 最长存活 = AT TTL（§7.1），无 Redis 档接受该窗口；验收用例明确"窗口内旧 AT 仍可用"为**符合预期**，不是缺陷。

### 13.6 合规要点 / 13.7 成本估算

### 16.4 必测异常路径清单（HBT / MEDIA / SANDBOX 三组）

**进度（HBT-001~006，见 §12.5）**——进度网关的关闭条件。

**票据与播放（MEDIA-001~008）**：
1. playlist TTL 过期后 fragment 403 → 换票成功，播放不中断；
2. key nonce 重放 → 403 REPLAY，第二次不吐 key；
3. ksession 换用户 lesson → MISMATCH；
4. 超管 preview ticket → 进度 `source=preview`，报表不计入；
5. CDN 不可达 → fallback_urls 逐次尝试成功；
6. ts 长 TTL（24h）内重复访问 → 200 命中，验证"长 TTL 不导致越权"（因为 key 仍短 TTL）；
7. iOS 原生 HLS 取 key（无 Authorization 头）→ 成功；
8. 会员降级期间换票 → `profile_allowed` 实时收缩，旧 master 失效。

**沙箱（SANDBOX-001~006）**：
1. 畸形 mp4（超长 box / negative size）→ 检疫拒，不进队列；
2. 恶意文件试图 `http://169.254.169.254/...` → 沙箱无网，解析失败；
3. 试图 `mount` / `ptrace` 的系统调用 → seccomp 杀进程，exit≠0，job failed；
4. 输出 ts 含非 H.264/AAC 流 → 二次 ffprobe 拒，asset 不标 ready；
5. 转码 OOM（构造高压缩率文件）→ cgroup 限 2G，进程被杀，job 重试≠崩溃 web；
6. keyinfo 泄漏面检查 → 沙箱内 `/proc`、`/etc` 不可读，退出 shred 生效。

**必测回归**：上传断点/秒传/缺片、交卷断网幂等、题目禁用快照、支付回调乱序、插件 disable 路由 404、模式切换 4 类冲突、导入冲突默认 report_only。

## 二十一、CDN 与视频分发架构（Q2）

### 21.1 ~ 21.2

21.1 带宽口径按 §1.4 峰值估算（HLS 分片拉流 750 req/s ≈ 7.5 Gbps @720p），内网档须客户书面确认并发上限。**21.2 分发链路**：

```
FFmpeg 产出 → 对象存储（私有读写）
                 ▲ 回源（私有鉴权，仅 CDN + origin 回落账号可访问）
                 │
客户端 ──HTTPS──▶ CDN 边缘 ──▶ ts（长缓存 24h~7d）✅   master.m3u8/var.m3u8（5~15min，可缓存 ✅）
                                 key 请求（URI 含 ks/n）──▶ 边缘回源到应用 ──▶ 应用鉴权吐 16 字节
                                                                    （no-store，永不进 CDN 缓存）
```

**关键点**：m3u8 **允许进 CDN**。m3u8 里的 key URI 用的是**匿名 kid + 短期 ksession 票据**，不含用户可辨认信息，且 ksession 由 nonce 保单次、playlist TTL 仅 5~15min——边缘缓存命中的是"同一份 playlist 字节"，不同用户拿到的 m3u8 **内容相同**，不存在"带用户票据进 CDN"的越权风险。这是把回源比压到极低的前提。

三类资源策略：

| 资源 | 缓存 | 鉴权 | 说明 |
|---|---|---|---|
| `*.ts` | **24h~7d** | CDN URL 鉴权（签名参数可长期有效，因 key 仍短 TTL） | 密文，泄露价值低；长 TTL = 高命中 |
| `*.m3u8` | **5~15min**，`private, no-transform` | CDN 鉴权 + 短 playlist_ttl | **可进 CDN**，variant 不携带用户票据 |
| `enckey` | 0 | 应用：ksession + nonce + 决策哈希 + AT（query-string 兼容原生 HLS） | 永不进 CDN，`no-store` |

### 21.3 CDN 配置清单

- 参数处理：**保留**鉴权参数 `auth_key/ks/vp`，忽略其余 query → 命中率与防盗同时成立；
- 压缩：ts/m3u8 **不 gzip**（不变）；
- 回源：`media.key` 路径**禁止** CDN 缓存（`Cache-Control: no-store` 由源站强制，CDN 侧再配一条 `location ~ key/` 的 0 缓存规则双保险）；
- 边缘 `X-Cache-Status` / `CF-Cache-Status` 类响应头**必须透传**，供 `doctor` 抽样判断 m3u8/ts 是否真的命中（验收依据）；
- 用量封顶、频次、WAF 按既定配置。

### 21.4 签名实现：两套后端、一个票据接口

#### 21.4.1 鉴权维度

`CdnAdapter.sign_url()` 的绑定因子：**`(path, expires_at, ksession_id, rand)`**；`ip_family` **只做记录与弱关联**，校验不匹配只 `logger.warning + metrics.inc("ticket_ip_drift")`，**不返回 403**。理由：4G/5G 切基站、微信内 WebView 连接复用、企业出口 NAT 重绑都会漂 IP，硬绑 = 移动端"看两分钟就死"。等保若要求强绑定，走 `media.ksession.strict_ip=true` + 客户端"网络切换后静默换票"，仍不拒旧票。

#### 21.4.2 三层 TTL 配置

```python
MEDIA_TTL_TS       = env.int("ZHY_MEDIA_TTL_TS",       86400*3)   # 3天，可到7天
MEDIA_TTL_PLAYLIST = env.int("ZHY_MEDIA_TTL_PLAYLIST",  900)      # 15分钟
```

#### 21.4.3 续签协议（客户端契约）

```
播放器          前端 TicketedHls           服务端
 │  fragment 403 / playlist 403 │                          │

 │                              │  重判 AccessPolicy       │
```

### 22.1 范围界定

### 22.2 方言差异补充（编号续接 5.2）

| # | 差异点 | openGauss 5.x / 6.x | openGauss 7.0 LTS | KingbaseES V9 (PG 模式) | 统一做法 |
|---|---|---|---|---|---|
| **D21** | `ON CONFLICT ... DO UPDATE` | ❌ 语法报错 | ✅（7.0 起对齐 PG 9.5+ 语义） | ✅ | `upsert()` 按 **flavor 运行时分派**，不按 `dialect()` 粗分；5/6 走 D21b，7.0/PG/KB 走 D21a；CI 三档全跑 |
| **D21a** | PG 式冲突子句 + `RETURNING id` | 不可用 | ✅ | ✅ | 仅在 `cap.upsert_conflict_clause && cap.returning` 同时为真时生成 |
| **D21b** | MySQL 风 `ON DUPLICATE KEY UPDATE` | ✅（且**不可更新唯一键/主键列**，同批自冲突报错） | 亦可用（兼容） | ❌ 非语法 | openGauss 5/6 专用分支；更新列白名单剔除自然键与 PK |
| **D21c** | upsert 后**取受影响行 id** | ❌ 无 RETURNING | ✅ | ✅ | **统一不假设能取到**：返 `UpsertResult(pk=None)` 时调用方 **必须** `rehydrate_by_natkey()`；这是类型级约束 |
| D22 | 认证 | SHA-256（`password_encryption_type=2`），原生 psycopg2 直连失败 | 同族 | scram/md5（PG 兼容） | 安装期探活 + 可读报错；厂商驱动进离线包 |
| D23 | 空串/NULL | PG 族语义 | 同 | **仅 `database_mode=pg` 时 PG 语义**；ora 模式 `ora_input_emptystr_isnull` 污染 | 只承诺 pg 模式；`COALESCE(col,'')=''` 判空；安装期双 `SHOW` 阻断 |
| D35 | `RETURNING` | 5/6 ❌，7.0 ✅ | ✅ | ✅ | `DialectCap.returning`（D2a） |
| 其余 D24~D34 | | | | | 常规规约，无语义差异 |

> **为什么这条必须写这么细**："走 MySQL 风 ON DUPLICATE KEY UPDATE、业务零改动"这个结论本身对，但容易漏掉"**无 RETURNING → flush 取不到刚插行的 id**"。进度网关、答题 attempt 编号、任何"插完立刻读自己 id"的路径都会踩这个坑。用 `UpsertResult.pk: PKType | None` 把"能不能拿到"变成编译期必须处理的分支，配合 72 条矩阵用例锁死。

### 22.3 适配层落地改动

```python
# core/db/compat.py
class Flavor(Enum):
    sqlite = "sqlite"
    mysql = "mysql"
    postgresql = "postgresql"
    opengauss_5 = "opengauss_5"   # 5.x
    opengauss_6 = "opengauss_6"   # 6.x
    opengauss_7 = "opengauss_7"   # 7.0 LTS+
    kingbase = "kingbase"         # V9 PG 模式

def flavor() -> Flavor:           # 启动时从 sys_compat_flags 读，不猜
    ...

CAPS: dict[Flavor, frozenset[Cap]] = {
    Flavor.opengauss_5: {Cap.upsert_on_duplicate, Cap.native_json, ...} - {Cap.returning, Cap.upsert_conflict_clause},
    Flavor.opengauss_6: {Cap.upsert_on_duplicate, ...} - {Cap.returning, Cap.upsert_conflict_clause},
    Flavor.opengauss_7: {Cap.returning, Cap.upsert_conflict_clause, Cap.native_json, ...},
    Flavor.kingbase:    {Cap.returning, Cap.upsert_conflict_clause, Cap.native_json, ...},
    # sqlite/mysql/postgresql 见 5.2
}
```

`upsert.py` 编译三路（伪码）：

```python
def upsert(model, values, natkey_cols, update_cols=None):
    cap = compat.cap
    stmt = insert(model.__table__).values(_project(values, natkey_cols, update_cols))
    if cap(Cap.upsert_conflict_clause) and compat.flavor() in PG_CONFLICT_FLAVORS:
        stmt = stmt.on_conflict_do_update(            # PG / OG7 / Kingbase
            index_elements=[model.__table__.c[c] for c in natkey_cols],
            set_=_exclude_pk_and_natkey(update_cols or values, model))
        if cap(Cap.returning):
            stmt = stmt.returning(model.id)
            row = session.execute(stmt).first()
            return UpsertResult(created=bool(row), pk=row[0] if row else None, version=...)
        session.execute(stmt)
        return UpsertResult(created=True, pk=None, version=...)   # ← 调用方必须能处理 pk=None
    elif cap(Cap.upsert_on_duplicate):                             # MySQL / OG5 / OG6
        stmt = stmt.prefix_with("IGNORE") if _is_insert_ignore(model) else stmt
        # OG5/6：用 dialect-specific "ON DUPLICATE KEY UPDATE ..."，更新列剔除自然键与 PK
        stmt = _mysql_upsert(stmt, model, natkey_cols, update_cols)
        session.execute(stmt)
        return UpsertResult(created=True, pk=None, version=...)   # LAST_INSERT_ID 不含被更新行
    else:                                                         # 兜底：应用层
        return _app_upsert_slow(model, values, natkey_cols, update_cols)
```

**兜底路径 `_app_upsert_slow`**：`SELECT ... FOR UPDATE`（PG/MySQL，SQLite WAL 下用独占 BEGIN）判冲突 → INSERT 或 UPDATE；捕获 `IntegrityError` 重试 2 次。**只在 CI 里跑，不允许生产高频命中**——若命中说明能力位探测错了，属于 installer bug，告警。

**安装期探测（不变形）**：`sys_probe` 临时表跑：insert→冲突更新→按自然键回读 id 一致 / JSON 读写 / UTC 时间 / lower like / 截断行为 / RETURNING 是否真可用（D2a）/ ON CONFLICT 是否真可用（D21）。结果写 `sys_compat_flags(flags JSONB, probed_at, flavor, og_version, kb_version_nullable)`，**运行时只读此表**。

| 项 | 说明 |

### 22.6 明确禁止

黑名单（厂商扩展函数、Oracle 语法、裸 `ON CONFLICT`/`ON DUPLICATE`）另加：

- 禁止 `session.flush()` 后**无条件**读 `obj.id` 当"刚插行的 id"，除非 `cap.returning` 为真且走 `upsert()` 返回路径；
- 禁止在业务代码里 `from sqlalchemy.dialects import postgresql` 做版本分支；分支只许在 `core/db/upsert.py`；
- 禁止用 `Insert.returning()` 直接拼 SQL 字符串；
- 禁止假设"upsert 一定创建了行"：`UpsertResult.created` 在 `pk=None` 时必须按"可能只是更新了旧行"处理。

## 附录 E · 插件 manifest JSON Schema（核心约束片段）

字段约束如下（`core/plugin/manifest.py` 加载期校验，失败即 `PLUGIN_MANIFEST_INVALID`，不进启用态）：

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["code","name","version","core_api_min","entry_server","supported_modes","capabilities"],
  "properties": {
    "code":         { "type":"string", "pattern":"^[a-z][a-z0-9_]{2,63}$" },
    "version":      { "type":"string", "pattern":"^\\d+\\.\\d+\\.\\d+$" },
    "core_api_min": { "type":"string" },
    "supported_modes": { "type":"array", "items":{ "enum":["internal","external"] } },
    "capabilities":  { "type":"array",  "items":{
        "enum":["progress:read","progress:report","media:ticket:issue",
                "access:evaluate","config:read","log:read"] } },
    "entry_web":     { "type":"string", "pattern":"^web/(?:[^/]+/)*[^/]+\\.(?:js|mjs)$" },
    "routes":        { "type":"array", "items":{ "pattern":"^[a-z0-9_]{1,64}$" } },
    "menu":          { "type":"array", "items":{
        "required":["title"],
        "properties":{
          "title":{ "type":"string", "minLength":1 },
          "path": { "type":"string", "pattern":"^/(?!.*\\.\\.)" },
          "permission":{ "type":"string", "pattern":"^[a-z][a-z_]*:[a-z][a-z_]*$" } } } }
  },
  "allOf": [
    { "comment":"capabilities_v2.progress_direct_write=true 且无核心团队签名 → 拒装" },
    { "not": { "properties": { "capabilities_v2": {
          "properties": { "progress_direct_write": { "const": true } } } } } }
  ]
}
```

| `capabilities_v2.*` | 允许值 | 违规处置 |
|---|---|---|
| `progress_direct_write` | 仅 `false` | 拒装 `PLUGIN_CAP_DENIED`（禁止绕进度网关） |
| `db_ddl` | 仅 `false` | 拒装（建表只能走插件独立迁移链） |
| `ffmpeg_direct` | 仅 `false` | 拒装（必须 `core.media.runtime.run_sandboxed`） |
| `upsert_raw_sql` | 仅 `false` | 拒装（禁止裸 `ON CONFLICT` / `ON DUPLICATE`） |

> 校验器对 manifest 源文本里出现的 `ON CONFLICT` / `ON DUPLICATE KEY UPDATE` / `RETURNING` 令牌**直接拒绝**，与 CI 的 `scripts/check_dialect_compat.py` 共用同一份黑名单，避免"插件把方言 SQL 藏进字符串拼接"。

补充约束（`core/plugin/manifest.py` 落地）：

- `table_prefix` 缺省派生 `plg_<code>_`；显式声明其它值 → `PLUGIN_TABLE_PREFIX_INVALID`，安装期实际建表也必须是该前缀；
- `core_api_min` 高于内核 `__version__` → `PLUGIN_MANIFEST_INVALID`；
- `entry_server` 必须是插件目录内的 `.py` 相对路径且文件存在；
- `entry_web` 必须位于 `web/` 目录下、后缀为 `.js`/`.mjs`、且文件存在；前端只能经 `/api/v1/plugin/<code>/assets/...` 读取 `web/` 内的代码/样式/字体（`no-store`，未启用 404）；
- `menu.path` 必须是站内绝对路径（`/` 开头，禁 `..`），`menu.permission` 必须是 `<资源>:<动作>` 权限码，前端据此显隐；
- `capabilities_v2` 出现未知键 → `PLUGIN_MANIFEST_INVALID`。

## 附录 H · 术语表

| 术语 | 含义 |
|---|---|
| **票据（ticket）** | 一次播放会话的短期凭证集合：`ksession_id` + playlist URL + key URL + TTL，取代裸签名 URL |
| `ksession` | 绑定用户/课时/访问决策的取 key 会话，单次 nonce，**不含**可猜测的用户标识 |
| **三层 TTL** | ts（长，24h~7d）/ playlist（中，5~15min）/ key（短，120s，nonce 单次） |
| **进度网关（ProgressGateway）** | 业务唯一进度写入入口：分配 `gw_seq` → 入总线 → 单写者 flush |
| `gw_seq` | 进度流水全局单调序号；缺口即丢进度，是对账基准 |
| `learn_progress_log` | 追加-only 事实源；`learn_progress` 是它的投影，可重建 |
| **单写者（single flusher）** | 每 shard 仅一个 flush 持租约写 `learn_progress`，消除多 writer 覆盖 |
| **沙箱八层** | §10.3.2.3：检疫 / 降权 / 无网 / seccomp / 资源 / 输出白名单 / 密钥隔离 / 失败处置 |
| **能力位（cap）** | `sys_compat_flags` 固化的方言能力，运行时只读，禁止按版本号猜 |
| **flavor** | 细粒度方言：`sqlite/mysql/postgresql/opengauss_5/6/7/kingbase`，区别于粗 `dialect` |
| `UpsertResult.pk=None` | upsert 未取到行 id 的**合法**状态（openGauss 5/6 常态），调用方必须处理 |
| **指标口径版本** | `metric_version=zhy-progress-v2`，报表与导出页眉带版本，可追溯 |
| **预览态（preview）** | 超管 `preview=true` 票据播放，进度标 `source=preview`，永不进统计（9.4 #18） |

## 附录 I · 资料来源与事实口径

**来源**：Vue 2 EOL、Element Plus/Vue 3、Flask 3.1、SA 2.0 稳定线 vs 2.1 预发布、方言版本支持、RETURNING 支持矩阵、openGauss/Kingbase 厂商文档与社区实践、Alembic 1.20.x。上述结论以目标实例 M0 Spike 实测为准。

**事实口径与复核要求**：

- **openGauss `ON CONFLICT` 支持边界**：社区 GaussDB/openGauss 兼容文档与 7.0 LTS 发布说明确认 7.0 起补齐 PG 式 `ON CONFLICT DO [NOTHING|UPDATE]`；5.x/6.x 仅接受 MySQL 兼容 `ON DUPLICATE KEY UPDATE`，且被更新行不得含唯一键/主键列、同批自冲突会报 `duplicate key`。**实施前必须在目标小版本容器里跑 T-DB-OG-001/101 复核**，不可仅凭"7.0 系列"字样推断。
- **openGauss RETURNING**：5.x/6.x 的 INSERT RETURNING 在多数打包版本中不可用（与 PG 9.2 基线的语句解析差异），7.0 随 PG 兼容度提升而可用；以 `sys_probe` 的 D2a 用例结果为准，不由版本号推断。
- **KingbaseES V9 PG 模式**：金仓 V9 手册确认 SQLAlchemy 方言包基于 ksycopg2、`database_mode=pg` 下空串与 NULL 严格区分、`ora_input_emptystr_isnull` 仅在 ora 模式生效；V8R6 行为与 V9 存在差异，故本稿不承诺 V8R6。
- **FFmpeg 安全面与沙箱依据**：近两年 FFmpeg 解码器/解析器链路持续有堆溢出类 CVE 披露（demuxer、HLS 解析、字幕/图片编码器等）。本稿 **不引用具体 CVE 编号作为"已全修复"的证据**——CVE 是流动的，故采用"版本固定 + SBOM + 无网 seccomp 沙箱 + 二次 ffprobe + CVE 命中即停任务"的工程对策，而非"升级到某版本即可"。上线前须以 `osv-scanner` 对 `zhy-ffmpeg-sbom.json` 复扫一次并把结果附进交付包。
- **hls.js fragment 鉴权与续签**：hls.js 默认 `xhrSetup` 对 **playlist 与 key** 生效，对 **fragment 请求**走内部 loader、自定义行为需覆写 `fLoader`/`xhrSetup` 组合；iOS `HTMLVideoElement` 与原生 `<video>` 取 key **不经过页面 XHR**，故 key 票据必须同时支持 query-string。`canPlayType('application/vnd.apple.mpegurl')` 为真时交由原生 MSE 路径。上述为 hls.js / HTML 规范层面的稳定行为，已在 23.7 P0 真机用例锁定。
- **进度一致性模型**：单写者 + 追加日志 + GREATEST 幂等是业界标准做法（借鉴事件溯源的"日志即真相、投影可重建"）；本稿把 `progress_log` 当事实源、`learn_progress` 当投影，因此"多 worker 崩溃不丢"成立。该模型在 SQLite WAL + 单写者下同样成立，不依赖 MVCC。
- **待校验项（上线前必做）**：① 目标 openGauss 小版本 T-DB-OG-001/101；② Kingbase V9 `libkci.so` 在客户 OS（麒麟/统信 + ARM64）可加载；③ 客户是否禁 seccomp（决定 24.3 的降级策略）；④ CDN 厂商 URL 鉴权公式与参数名（21.4 给的是形态，不承诺逐厂商一致）；⑤ hls.js 锁定小版本的 fragment loader 行为（写进 `packages/media/package.json` 锁死）。
